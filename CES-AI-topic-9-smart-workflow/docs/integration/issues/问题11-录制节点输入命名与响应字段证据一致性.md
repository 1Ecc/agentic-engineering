### 问题 11：录制节点输入命名与响应字段证据一致性

#### bug专题：同业务录制生成的 NodeDefinition 存在输入名错位与无证据中间字段映射

**问题描述**：

用户对比 `data/recordings/rec_1778664090416.json` 与 `data/recordings/rec_1778723054312.json` 后发现，两者业务意图相同，生成的节点类型也都是 `serviceforce.query_customer_order`，但 `converted_node.handler` schema 差异较大。

当前疑问：

- 同一个录制 session 内，`llm_trace.converted_node`、前端 Step 3 `specJson`、注册到节点市场后的 `data/nodes` 节点是否应该一致。
- `rec_1778723054312` 失败是否是 LLM 节点总结问题、录制响应体缺失问题，还是 `ApiCaptureSpec -> NodeDefinition` 转换问题。
- 以真实业务命名为准时，NodeDefinition 的 `inputs` 与 handler 模板里的 `{{ inputs.* }}` 必须保持一致。

复现场景：

```text
npm run debug:recording-node -- rec_1778723054312 service_order_id=202604273400100002
```

返回：

```json
{
  "code": "DATA_NOT_FOUND",
  "platform": "serviceforce",
  "step": "serviceforce.query_customer_order",
  "message": "serviceforce.query_customer_order 未映射到输出字段 soid",
  "details": {
    "output": "soid",
    "mapping": "$.data[0].soid"
  }
}
```

而旧断点：

```text
npm run debug:recording-node -- rec_1778664090416 service_order_id=202604273400100002
```

可返回：

```json
{
  "jiuqiu_order_no": "RETAIL20260430000023"
}
```

**当前态**：

- 同一个 session 内，理论链路应为：
  - `recording.llm_trace.converted_node`
  - 前端 Step 3 当前 `specJson`
  - 注册后的 `data/nodes/<type>.json`
  三者应在注册当下保持一致。
- 不同 session 之间不保证一致，即使 `type` 相同；同名节点注册到节点市场时还可能覆盖旧定义。
- 两个 case 的业务请求均未采集到 `responseBody`：
  - `GetServiceOrderList` 的 `responseBody` 为空。
  - `customerOrder/list` 的 `responseBody` 为空。
- `rec_1778723054312` 的 LLM `notes` 已声明：`$.data[0].soid` 与 `$.data[0].orderNo` 是缺少响应体情况下的假设，需要确认。
- 当前真实接口验证结果：
  - `GetServiceOrderList` 顶层返回结构包含 `rows`、`total`、`duration`、`code`、`msg`、`error`，不是 `data`。
  - 因此 `$.data[0].soid` 在真实响应上取不到。
  - `customerOrder/list?soId=202604273400100002` 可直接返回 `data[0].orderNo = RETAIL20260430000023`。
- SOP1 文档与实际代码均以历史工单列表作为服务云入口：
  - `docs/api/sop1-network-capture.md` 的最小链路第 1 步是 `GET /fieldserviceapi/api/ServiceOrderHis/GetServiceOrderHisList?soid={work_order_no}`。
  - `packages/connectors/src/serviceforce.ts` 的 `getPaidJiuqiuOrder` 首先调用 `ServiceOrderHis/GetServiceOrderHisList` 获取历史工单信息与 `passKey`。
  - 随后 SOP1 直接调用 `customerOrder/list?soId={work_order_no}` 获取客户订单与九丘订单号。
- `rec_1778664090416` 与 `rec_1778723054312` 的原始请求、过滤后请求、LLM prompt 输入中都包含 `GetServiceOrderHisList`、`serviceOrderHistory/detail` 与 `customerOrder/list`，但 LLM 最终都选择了当前工单列表 `GetServiceOrderList` 作为 selected_request/step1。
- 当前工作区中保存的两个 `converted_node` 都出现过输入名与模板引用不一致：
  - `rec_1778723054312` 保存的 `converted_node.inputs` 为 `service_order_id`，但 step1 仍引用 `{{ inputs.soid }}`。
  - `rec_1778664090416` 保存的 `converted_node.inputs` 与历史断点输出存在差异；用当前转换函数从 `parsed_output` 内存重转时可得到自洽的 `service_order_id` 输入与模板。
- 当前 `apiCaptureSpecToNodeDefinition` 的多步转换逻辑会保留 `steps` 原始模板；如果 LLM 在 `spec.inputs`、`node_mapping.inputs`、`steps[*].query_template` 中给出不同输入名，现有验证无法发现。

**期望态（需要跟用户沟通确认）**：

- 同一个 session 内，`converted_node`、前端 `specJson`、注册节点必须一致；注册行为只保存当前页面确认过的那份 NodeDefinition。
- NodeDefinition 的 `inputs` 是运行时真实输入 schema 的唯一准入；所有 `{{ inputs.* }}` 必须引用 `inputs[].name` 中存在的字段。
- 如果 LLM 输出的 `spec.inputs`、`node_mapping.inputs`、`query_parameters.input_name` 存在命名差异，转换阶段必须统一到同一个真实输入名，并同步重写模板引用，或直接 validation fail。
- 当录制数据缺少 responseBody 时，不能生成后续步骤强依赖的中间 `response_mapping`，除非有明确证据证明该字段来自前序响应。
- 如果后续请求参数值等于用户输入值，例如 `customerOrder/list?soId=202604273400100002` 与输入工单号一致，应优先复用 `{{ inputs.<工单号字段> }}`，不要假设它来自 `steps.step_list.soid`。
- 对 `rec_1778723054312` 这类通用流程表达，允许保留 step1 作为业务流程证据，但在缺少响应体证据时，step2 参数应采用已观测到的真实参数来源，而不是无证据中间字段。
- 录制链路中的业务请求 `responseBody` 必须完整回填；不能把 telemetry、MCP 详情、日志预览等已经截断的片段当作完整响应证据。只有完整、可解析、可被 JSONPath 命中的响应体才能让 `response_summary.body_available=true`，并支撑运行时 `steps[].response_mapping`。

**分析与解决**：

本问题由三类因素叠加：

1. 录制证据层：两个 case 都没有采集到关键业务响应体。LLM 无法基于真实 response body 判断 `GetServiceOrderList` 到底返回 `data[0].soid`、`rows[0].soId`，还是其他字段。
2. LLM 生成层：`rec_1778723054312` 选择了更“流程化”的推理：step1 查列表、从 step1 响应提取 `soid`、step2 用 `steps.step_list.soid` 查客户订单。这种思路在通用场景里合理，但缺少响应体证据时不可靠。
3. 转换/校验层：当前转换与校验没有强制检查 `inputs[]` 与所有 `{{ inputs.* }}` 模板引用一致，也没有阻断“缺少响应体但生成必需中间字段映射”的情况。
4. 请求选择层：当前 LLM prompt 只提供录制请求列表与用户描述，不注入 `docs/api/sop1-network-capture.md` 的 SOP1 领域知识；在 responseBody 缺失时，LLM 无法知道当前工单列表返回空、历史工单列表返回有效结果，因此倾向选择用户描述中的“工单列表”对应的 `GetServiceOrderList`，而不是 SOP1 真实入口 `GetServiceOrderHisList`。

两个 case 的关键差异：

- `rec_1778664090416` 的 parsed_output 策略是保守路径：
  - step1 查询列表，但不从 step1 提取中间字段。
  - step2 直接用用户输入 `service_order_id` 作为 `soId`。
  - 该策略恰好符合真实接口行为，因此断点可跑通。
- `rec_1778723054312` 的 parsed_output 策略是通用流程路径：
  - step1 查询列表，并假设 `$.data[0].soid` 存在。
  - step2 使用 `{{ steps.step_list.soid }}`。
  - 但真实 step1 不返回 `data`，导致 `DATA_NOT_FOUND`。

初步解决方向：

- 在 `validateApiCaptureSpec` 或 `validateNodeDefinition` 中增加模板引用一致性校验：所有 `{{ inputs.xxx }}` 必须能在最终 `node.inputs` 中找到。
- 在 `apiCaptureSpecToNodeDefinition` 中建立输入名统一机制：以真实运行输入 schema 为准，同步替换 `steps`、`node_mapping.query_template`、`body_template`、`response_mapping` 中的输入引用。
- 增加 response evidence 规则：当 `response_summary.missing_response_body=true` 或 captured request 无 responseBody 时，禁止生成会阻断后续步骤的必需中间 `response_mapping`；若必须生成，应标记为待确认并不允许直接注册/试运行为可用节点。
- 优化 LLM prompt：如果后续请求中的参数值与用户输入值一致，且缺少前序响应体证据，优先复用用户输入，不要臆造前序响应字段。
- 优化多请求选择规则：当同一业务链路同时出现当前列表、历史列表、历史详情、客户订单接口时，应根据真实用户操作链路和接口名称识别历史工单路径；至少在 prompt 中要求 LLM 不要只选择第一个列表接口，而要解释为何排除 `GetServiceOrderHisList`。
- 若目标业务属于已知 SOP1 场景，可考虑向 LLM 提供 SOP1 network capture 摘要作为 few-shot/领域参考；否则当前通用录制器不会自动复用 SOP1 文档中的接口策略。
- 后续可考虑增强 MCP 录制能力，尽量采集业务 API responseBody，降低 LLM 猜测空间。

**问题分析线路与方法论沉淀**：

本问题的价值不只在于修复 `soid`/`soid_list` 映射错误，更在于形成了一套排查“录制证据 -> LLM 总结 -> 确定性转换 -> 运行试调”的方法论。

实际分析线路如下：

1. 先从运行现象出发，而不是直接改 prompt。
   - 用户先发现前端录制试调用、节点市场试运行都返回空值或固定值。
   - 随后通过 `npm run debug:recording-node -- <recording_id> service_order_id=...` 做后端断点复现，确认问题不是单纯前端展示问题。
   - 这个动作把问题从“前端试运行异常”收敛为“同一类录制节点在运行时映射失败”。

2. 对比成功 case 与失败 case，先找结构差异。
   - `rec_1778664090416` 可返回 `jiuqiu_order_no=RETAIL20260430000023`。
   - `rec_1778723054312` 报 `DATA_NOT_FOUND`，失败点是 `$.data[0].soid`。
   - 对比后发现两者业务意图相同，但 `converted_node.handler.steps` 和 `response_mapping` 明显不同：成功 case 更保守，直接复用输入工单号；失败 case 假设前序列表接口会返回 `soid`。
   - 由此确认问题不是“接口完全不可用”，而是“生成出的运行链路存在无证据中间字段依赖”。

3. 分清同一 session 内的一致性与不同 session 间的差异。
   - 同一录制 session 内，`llm_trace.converted_node`、前端 Step 3 `specJson`、注册后的 `data/nodes/<type>.json` 理论上应保持一致。
   - 不同 session 即使业务意图和 `type` 类似，也可能因用户描述、抓包证据、LLM 输出不同而生成不同节点。
   - 这个判断避免把“不同录制生成不同节点”误判为前端状态同步 bug。

4. 用真实接口和 SOP1 既有代码/文档做事实基线。
   - 通过 SOP1 代码确认真实策略是 `ServiceOrderHis/GetServiceOrderHisList -> customerOrder/list`。
   - 通过 `docs/api/sop1-network-capture.md` 确认当前工单列表为空，历史工单列表有结果，客户订单接口返回 `data[].orderNo`。
   - 通过真实接口行为确认 `GetServiceOrderList` 顶层是 `rows/total/code/msg`，不是 `data`，所以 `$.data[0].soid` 必然失败。
   - 这一步把“LLM 猜错字段”从猜测变成可验证事实。

5. 再回到录制证据链，检查 LLM 到底看到了什么。
   - 检查 recording 中的业务请求，发现关键业务请求的 `responseBody` 缺失。
   - 这说明 LLM 的 `missing_response_body=true` 在它的输入视角下是成立的；它并不是忽略了响应体，而是没有拿到响应体证据。
   - 因此问题不能只归因于 LLM，还要继续查录制采集和过滤链路。

6. 追踪“文档有响应体、录制没有响应体”的差异来源。
   - 对比 `docs/api/sop1-network-capture.md` 后发现文档里确实有 Response 摘要。
   - 进一步解码 `app-analysis-tdp.lenovo.com/up` 监控上报，发现其中的 `xcontext.response` 包含真实 XHR 响应。
   - 当时判断为：过滤逻辑把 telemetry 请求整体过滤掉，导致可见响应证据没有进入 LLM 输入。
   - 后续九丘 case 证明该判断只解释了“为什么看不到响应体”，但不能解决“响应体必须完整”的根因；telemetry 只能作为排查线索，不能作为主证据。
   - 最终结论是：接口本身有响应体；当前录制链路必须从浏览器 Network 层把完整响应体直接转交给业务请求。

7. 修复证据入口，而不是放开所有噪声。
   - 直接把 telemetry 请求交给 LLM 会引入大量噪声和敏感字段风险。
   - 历史临时做法是：继续过滤 telemetry 请求本身，但在过滤前从 telemetry 中提取 `xcontext.response`，按 method、path、非系统 query 参数回填到对应业务请求的 `responseBody`。
   - 该做法已被 `rec_1778730863154` 证明不彻底：九丘 telemetry 只给 1500 字符截断片段，因此本轮已撤销 telemetry 回填，改为 MCP 详情路径完整 body 捕获。

8. 观察新一轮生成结果，继续区分“证据问题”和“schema 边界问题”。
   - 新录制 `rec_1778728420496` 因使用 `$.rows[0].passKey`、`$.data[0].orderNo` 这类真实且简单的 JSONPath，试运行 OK。
   - 新录制 `rec_1778728643621` 仍失败，失败点变成 `soid_list: $.rows[*].soid`。
   - 这说明响应体证据已进入链路，但 LLM 把“接口文档摘要字段”误塞进了运行时 `steps[].response_mapping`。
   - 问题层级从“缺证据导致猜字段”转移为“接口文档摘要和运行时映射边界不清”。

9. 最后收口 prompt 与 validation。
   - prompt 中明确 `response_summary` 只做接口响应结构摘要，参考 `docs/api/sop1-network-capture.md` 的 Response 摘要风格，但不保留样例值。
   - prompt 中明确 `steps[].response_mapping` 只放运行时必需字段：后续 step 要用的中间字段，或最终 outputs 需要的字段。
   - prompt 中明确 steps 是“最短必要执行链路”，不是 UI 操作回放；如果某个接口或更短链路已能稳定实现用户目标，应优先使用更短链路。
   - validation 中拦截当前 runner 不支持的 `$.rows[*].field` 通配 JSONPath，避免问题拖到试运行阶段才暴露。

10. `rec_1778730863154` 暴露出响应体回填仍不彻底。
   - 用户在九丘平台录制 `jiuqiu.order_detail_query`，运行时报 `jiuqiu.order_detail_query 未映射到输出字段 service_products`。
   - 生成的节点链路是 `order/list -> order/detail/{id}`，`service_products` 被映射为 `$.data.serviceProducts`。
   - 录制文件中 `/order/detail/11650722` 的 `filtered_requests.responseBody` 长度只有 1500 字符，截断在 `orderCustomer` 中间，末尾为 `..."name":"王康健","c$`，不包含真实的 `orderItem`、`pgi`、`so`、`s4ToSscmTime` 字段。
   - 九丘真实字段基线来自 `docs/api/sop1-network-capture.md` 和 `packages/connectors/src/jiuqiu.ts`：服务产品明细应在 `data.orderItem[]`，其中 PGI 为 `pgi`，S4 订单号为 `so`，PGI 抛送时间为 `s4ToSscmTime`。
   - 因此这不是节点注册丢失字段，而是响应体证据只回填了 telemetry 中已截断的 1500 字符片段，LLM 在缺少完整字段证据时猜出了 `serviceProducts`。

11. 方案收敛：只修响应体不完整这个根因。
   - 用户确认：不需要围绕截断响应体再堆多层兜底策略；根因是录制层没有拿到完整业务响应体。
   - `只记录 fetch/XHR/GraphQL/WebSocket`、`忽略 js/css/png/svg/font/analytics/sentry` 这类规则只负责筛掉非业务请求，不应该承担响应体补全职责。
   - 真正修复点只有一个：录制器必须通过 MCP 详情路径直接拿完整 response body。录制开始后以 `list_network_requests` 建立请求索引，再对业务请求 `reqid` 调用 `get_network_request(reqid, responseFilePath)`，从保存的响应文件读取完整 body 并写入原始录制文件；不能依赖日志预览或 telemetry 片段。
   - telemetry 中的 `xcontext.response` 不是可靠主证据。本 case 已证明九丘 telemetry 会把响应截到 1500 字符；因此 telemetry 不能再作为解决响应体完整性的方案，最多作为排查线索。
   - 后续问题 12 已修正方案：保留 `chrome-devtools-mcp` 作为录制实现，修复 MCP reqid 解析与 `responseFilePath` 完整 body 落盘路径。
   - 本轮代码修复：移除 `filterCapturedRequests` 中从 `app-analysis` telemetry `xcontext.response` 回填业务 `responseBody` 的逻辑，避免截断片段继续被当成完整证据。
   - 原始录制文件必须保存完整 body；若担心 LLM token，应该在送入 prompt 前基于完整 JSON 生成结构摘要，而不是截断录制证据本身。
   - 针对本 case 的验收标准：`/order/detail/{id}` 的录制响应必须包含 `data.orderItem[]`；LLM 看到的结构摘要必须能体现真实字段 `pgi`、`so`、`s4ToSscmTime`；不能再因为响应体截断生成无证据的 `$.data.serviceProducts`。

可复用的方法论：

- 先用运行命令复现，再看生成物，不直接猜 prompt。
- 先比较成功/失败 case 的最小差异，再判断问题在哪一层。
- 对 LLM 问题做分层：输入证据是否完整、prompt 是否表达清楚、schema 边界是否合理、转换/校验是否兜底、runner 是否支持该语法。
- 对“LLM 猜错”不要只改 prompt；先确认它是否看到了足够证据。
- 对“业务流程”和“最短可执行接口链路”分开判断：用户操作说明业务意图，但不要求运行节点复刻所有 UI 冗余路径。
- 文档性字段与运行字段必须分开：接口响应摘要可以描述结构，运行映射只能包含执行链路真正依赖的字段。
- 能在 validation 阶段拦截的问题，不要留到试运行阶段暴露。
