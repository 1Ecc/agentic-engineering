### 问题 10：录制节点试调用与多接口链路执行闭环

#### bug专题：多接口业务链路生成后无法试调用验证输出

**问题描述**：

用户测试“服务云中根据工单号查询九丘订单号”多接口业务链路。录制数据位于 `data/recordings/rec_1778662147672.json`。

业务意图：在服务云平台中，先基于工单号查询工单 list，再点击 list 进入工单详情页，在客户订单板块查询到九丘订单号。

前端已生成节点规范，用户认为生成结果基本可接受，但点击“试调用”时报错：

```text
Node type is not registered: serviceforce.query_customer_order
```

用户希望以该 case 为例补齐后端能力：点击试调用后出现简单测试入口，输入一个 input，然后展示 output，用于判断生成出的节点是否真的可用。

**当前态**：

- `rec_1778662147672.json` 中 LLM trace validation 与 node validation 均通过。
- 生成节点类型为 `serviceforce.query_customer_order`。
- 生成节点 handler 为 `recorded_http_flow`，输入为 `soid`，输出为 `jiuqiu_order_no`。
- 试调用走 `/api/nodes/:type/invoke`，该接口只从已注册节点市场 registry 中查找节点。
- 新录制完成但尚未注册的节点不在 registry 中，因此报 `Node type is not registered`。
- `recorded_http_flow` handler 仍未实现，多步录制节点即使注册后也无法真正执行。
- 2026-05-13 新断点 case 改为 `data/recordings/rec_1778664090416.json`；该 recording 已落盘 `llm_trace.converted_node`，类型为 `serviceforce.query_customer_order`，handler 为 `recorded_http_flow`，输入为 `service_order_id`。
- 前端仍可能因缓存或旧调用路径继续触发 `/api/nodes/:type/invoke`，本轮验证策略调整为先以后端断点命令验证，不再要求用户反复前端测试。
- `rec_1778664090416` 的 NodeDefinition 已能被后端直接读取和执行，`Node type is not registered` 已不再是当前后端断点问题。
- 当前真实试运行失败点收敛为服务云登录态失效：服务云业务响应返回 `code=401`、`msg=token失效`，后端已明确抛出 `AUTH_REQUIRED`。
- SOP1 已有统一鉴权能力：通过 `/api/auth/browser-login/start` 拉起持久化浏览器，用户登录服务云/九丘/SPOS 后，通过 `/api/auth/browser-login/finish` 保存登录态到本地 `AUTH_STATE_PATH`（默认 `secrets/auth-state.json`）；后续 SOP1 和通用 workflow/headless 请求均复用该登录态。

**期望态（已与用户本轮对齐）**：

- 录制完成后的草稿节点不需要先注册，也可以直接试调用。
- 试调用 UI 简单优先：根据节点 inputs 展示输入框；当前 case 只需要输入工单号。
- 点击试调用后，后端按草稿 NodeDefinition 执行 recorded_http 或 recorded_http_flow。
- 后端返回 output，并在前端展示，帮助用户判断“生成出的东西到底有没有用”。
- `recorded_http_flow` 至少支持顺序执行多步请求、步骤间引用和最终 output 映射。
- 录制节点的试运行/试调用本质上是正常业务接口访问，必须复用 SOP1 已有鉴权能力，不新建第二套鉴权逻辑。
- 当试调用遇到登录态失效时，前端和后端断点命令都应明确提示先走 SOP1 鉴权流程：拉起登录浏览器、用户完成对应平台登录、保存本地登录态，然后再重新执行试调用。
- 鉴权信息的读取继续走 SOP1 底座：headless 浏览器加载本地 storage state，并由 `requestJson` 根据平台/URL 推断必要请求头；录制节点执行器只复用该能力，不直接管理账号密码、token、cookie。
- 试调用链路后续需要有统一入口检查/引导登录态状态，但本问题内先以复用现有 `/api/auth/*` 能力和后端断点命令闭环为准，不额外开发新的登录方案。

**分析与解决**：

本问题不属于 LLM 生成质量本身，而是“生成后的节点验证闭环”缺失：

1. 前端试调用误用已注册节点调用接口，草稿节点尚未注册时必然查不到。
2. 后端缺少草稿节点直接调用入口。
3. `recorded_http_flow` 执行器尚未 ready。
4. 现有 `recorded_http` 执行器未渲染 `query_template`，会影响通过 query 参数传参的录制接口。
5. 真实业务接口试运行依赖平台登录态；当前 case 已越过 NodeDefinition 读取/执行问题，新的断点是服务云登录态失效。

实现方向：

- 新增草稿节点试调用 API，接收 `{ spec, inputs }`，先校验 NodeDefinition，再直接执行，不依赖 registry。
- 实现 `recorded_http_flow` 顺序执行器：
  - 每步渲染 `url_template`、`query_template`、`body_template`。
  - 每步执行后按 `response_mapping` 取值，写入 `steps.<step_id>` 上下文。
  - 后续步骤可使用 `{{ steps.step_id.field }}` 引用前序输出。
  - 最终按 flow `response_mapping` 输出结果。
- 修复 `ApiCaptureSpec -> NodeDefinition` 多步转换：多步 flow 不应使用全局 `node_mapping.query_template` 覆盖第一步自身的 `query_template`。
- 前端 Step 3 增加输入区，调用草稿节点试调用 API，并展示 JSON output。
- 试运行鉴权不新建能力，复用 SOP1 已有登录态流程：
  - 通过现有 `/api/auth/browser-login/start` 打开持久化登录浏览器。
  - 用户在浏览器中完成服务云、九丘、SPOS 等平台登录。
  - 通过 `/api/auth/browser-login/finish` 保存 storage state 到本地。
  - 后续 recorded_http / recorded_http_flow 执行时由 `openPersistentBrowser({ headless: true })` 加载本地登录态，并通过 `requestJson` 推断平台请求头。
  - 若接口返回 HTTP 200 但业务 JSON 表示登录态失效，也统一转换为 `AUTH_REQUIRED`，作为用户重新登录/保存登录态的明确断点。
