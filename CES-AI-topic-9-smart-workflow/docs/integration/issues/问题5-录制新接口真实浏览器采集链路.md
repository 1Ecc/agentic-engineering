### 问题 5：核心功能“录制新接口”当前不满足预期，需要参考 SOP1 的人工浏览器操作采集路线

**问题描述**：

问题 1 已确认当前架构分层本身没有问题：LLM 不是 MCP Client，真正的 MCP Client 应是后端或执行环境中的工具调用方。但这也暴露出新的核心问题：当前产品里的“录制新接口”能力，从实际联调结果看还不能满足预期，无法完整实现用户想要的接口录制闭环。

用户参考 SOP1 的历史路线：之前通过 Codex 调用 chrome devtools mcp，吊起浏览器；用户在浏览器中真实操作业务流程；Codex 基于 Chrome DevTools MCP 采集到的网络请求，总结出接口规范；后续再基于这些接口规范完成开发。

因此，本项目的核心功能本质上也应接近这条链路：平台负责拉起可操作浏览器并采集真实请求，用户负责在浏览器中完成业务操作，系统再将采集到的请求整理成接口规范，而不是依赖 LLM 自行“猜测”接口。

**当前态**：

- 问题 1 的架构澄清已验收，当前代码中 LLM 不作为 MCP Client 的判断是正确的。
- 但“录制新接口”作为核心功能，目前仍未达到 SOP1 路线中的真实可用状态。
- 当前需要重新确认产品目标：录制能力是否必须支持“拉起浏览器 → 用户手动操作 → 采集 Network → 生成接口规范”的完整闭环。
- 若该目标成立，则后续重点不应停留在文档澄清，而应转向真实浏览器录制链路的能力补齐与验收。

**期望态（已确认）**：

- 采用方式 A：产品化路线。平台后端作为 MCP Client，直接启动或连接 `chrome-devtools-mcp`，不依赖 Codex 作为产品运行时链路。
- `chrome-devtools-mcp` 作为 MCP Server，负责连接或拉起一个用户可操作的 Chrome 实例，并提供页面导航、Network 请求列表和请求详情等 DevTools 能力。
- 用户在该 Chrome 实例中完成目标平台的真实业务操作。
- 系统持续采集该会话中的 Network 请求与响应，并在结束录制后过滤、去重、归类。
- 系统基于采集结果生成接口规范草稿，包括请求方法、URL、headers、query/body、响应结构、关键字段含义和必要的调用顺序。
- LLM 只参与“请求分析与规范生成”，不承担浏览器控制或接口凭空推断。
- 生成结果应可被后续节点开发、工作流编排或接口文档沉淀复用。

**分析与解决**：

进一步判断后，这个功能的关键不是“让 LLM 作为 MCP Client”，也不是“产品运行时依赖 Codex”。SOP1 路线真正可复用的是一种工作模式：**系统打开一个用户可操作的真实浏览器，用户完成业务操作，系统捕获 Network 请求，最后由 LLM 基于真实请求生成接口规范**。Codex 在 SOP1 中承担的是临时调试和总结角色；产品化后，这个角色应沉淀为后端录制驱动与接口规范生成流程。

当前实现已经有 `startRecording` / `finishRecording` 的外壳，但还没有形成可验收的真实录制闭环，主要缺口如下：

1. `JsonRpcMcpClient` 目前假设存在 `MCP_SERVER_URL`，并假设服务端提供 `start_browser`、`start_network_recording`、`list_network_requests` 等 JSON-RPC 方法；但项目内没有明确 chrome-devtools-mcp 的启动、连接、健康检查和方法契约，存在“代码有调用点，但真实服务未被产品化接入”的风险。
2. `startRecording` 只返回 `recording_id` / `browser_id`，没有明确浏览器窗口是否已打开、打开在哪个目标地址、用户如何确认可以开始操作，也没有请求数轮询或录制状态查询接口。
3. 录制数据在 start 时只持久化空快照，真实请求依赖 finish 阶段一次性 `listNetworkRequests`；如果中途采集失败，用户无法及时感知。
4. `finishRecording` 捕获 MCP 请求列表失败时会退回空快照继续执行，最终可能只报 “No business API requests were captured”，会掩盖真实根因；核心链路应改为明确失败并返回 MCP 采集错误。
5. 当前只拿请求列表，没有明确补齐 request body / response body 的策略，也没有记录原始采集、过滤后采集和 LLM 输入之间的可追溯关系。
6. 前端 Step 2 只是“打开录制浏览器 / 完成录制”，还缺少目标入口、录制状态、采集条数刷新、失败原因展示、重新开始和取消清理等联调必需能力。

技术路线已确认：采用 **方式 A：产品化推荐**。后端作为 MCP Client 接入 `chrome-devtools-mcp`，由平台完成 MCP Server 启动、连接、工具调用和会话生命周期管理；Codex 只作为 SOP1 阶段验证过的参考路线，不进入最终产品运行链路。

实现方案建议按三层推进：

1. **MCP 接入层**：用 MCP SDK 或等价 transport 启动/连接 `npx -y chrome-devtools-mcp@latest`，确认 stdio / HTTP proxy 等实际 transport，并固化工具契约。不能继续假设存在普通 HTTP JSON-RPC 的 `MCP_SERVER_URL` 和自定义 `start_browser` 方法。
2. **录制编排层**：在 `node-recorder` 中抽象 `RecorderDriver`，由 `ChromeDevToolsMcpRecorderDriver` 调用 MCP 工具完成建页/导航、Network 请求读取、请求详情补齐、会话关闭和错误返回。
3. **规范生成层**：先把 MCP 采集到的真实请求整理为接口规范草稿，再由平台转换为 `NodeDefinition` 草稿，最后交给用户确认、试调用和注册。
4. **保留 LLM 的边界**：LLM 只消费过滤后的真实请求，输出节点规范草稿；LLM 不负责打开浏览器、不负责凭空补全接口、不负责吞掉采集失败。
5. **验收先于文档沉淀**：该问题属于核心联调问题，PRD 和技术方案应等最小闭环跑通并经用户验证后再更新。

#### bug专题：录制期间 requests 无法落盘

**问题描述**：

录制新接口时，`startRecording` 初始落盘 `requests: []` 属于正常状态；但用户在录制浏览器中完成真实业务操作后，前端仍显示 `MCP 真实浏览器 · 状态：recording · 已捕获 0 条请求`，对应 `data/recordings/rec_xxx.json` 中 `requests` 仍为空。进一步点击完成录制时出现 `Recording session is not active: rec_xxx`，说明至少存在“采集数据未落盘”和“录制会话状态不可用”两个需要区分的现象。

**当前态**：

- `startRecording` 会创建 `rec_xxx`，启动 MCP driver，并将 driver 存入当前 Node 进程内的 `activeRecorders`。
- `startRecording` 初始持久化文件时，`requests: []` 是预期行为。
- 前端每 3 秒轮询 `GET /api/nodes/record/:id/status`；理论上该接口应通过 `activeRecorders` 中的 driver 读取 MCP Network，并持续更新 `request_count` 与落盘 `requests`。
- `finishRecording` 会最后再读取一次 MCP Network，然后执行 `cleanupSession` 并从 `activeRecorders` 删除该录制会话。
- 当前问题显示：用户业务操作后 `requests` 仍为空，且 finish 阶段可能已经拿不到 `activeRecorders` 中的 driver。

**期望态（已确认）**：

- 本轮只排查“业务操作期间 Network 数据为什么没有从 MCP 落到 `requests`”这一节点。
- 后续的业务请求过滤、LLM 提取、节点规范校验、节点注册暂不参与本轮分析和修改。
- 在用户辅助完成真实浏览器操作后，状态轮询或 finish 前的最后一次读取至少应能让 `requests` 从 `[]` 变为非空。
- 如果 `requests` 仍为空，系统必须能定位是会话失活、读错页面、MCP 无原始请求、原始请求解析失败，还是落盘更新失败。

**分析与解决**：

本轮 debug 先按证据链分层，不急于修改业务逻辑。核心判断口径如下：

1. **会话生命周期节点**：确认 `start/status/finish` 是否都命中同一个 API 进程，以及 `activeRecorders` 中是否仍有该 `recording_id` 对应的 driver。若 status 返回 `Recording session is not active in this process` 或 finish 报 `Recording session is not active`，优先怀疑 API 进程重启、多进程访问、首次 finish 后已 cleanup、或 driver 异常关闭。
2. **轮询触发节点**：确认前端轮询是否真的持续请求 `GET /api/nodes/record/:id/status`，以及 API 返回的是实时 MCP 采集结果，还是仅返回落盘旧快照。
3. **MCP 读取节点**：确认 driver 的 `listCapturedRequests` 是否被调用，是否成功执行 `select_page` 与 `list_network_requests`。
4. **页面选择节点**：确认 MCP 读取的 pageId 是否就是用户实际操作的 Chrome 页面。若用户操作页和录制页不同，MCP 可能正常工作但一直读到 0 条。
5. **原始 Network 节点**：确认 MCP 原始返回是否有 `reqid=... METHOD URL [status]` 或结构化 `networkRequests` 数据。若原始返回为空，问题在 MCP/页面/浏览器；若原始非空但转换后为空，问题在解析。
6. **落盘节点**：确认 status 或 finish 拿到的 requests 是否写回 `data/recordings/rec_xxx.json`。若内存返回非空但文件仍为空，问题在持久化更新。
7. **finish 二次现象**：若第一次 finish 已进入 cleanup，即使后续因为 0 请求失败，再次点击完成录制也会报 `Recording session is not active`。因此需要区分“第一次 finish 的真实错误”和“重复 finish 的二次错误”。
