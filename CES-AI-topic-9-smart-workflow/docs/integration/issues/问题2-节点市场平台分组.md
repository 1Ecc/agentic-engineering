### 问题 2：节点市场——已接入平台应按平台分组展示

**问题描述**：

当前节点市场的"已接入平台"分组把所有 connector 节点平铺展示（服务云查询、九丘查询、SPOS 查询并列），没有体现**平台层级**。实际业务逻辑中，每个平台（服务云、九丘、SPOS）可能未来有多个接口/节点，应该按"平台 → 接口列表"的结构展示。

**当前展示**（❌ 平铺）：

```
▼ 已接入平台（3）
  🏢 服务云查询    🏢 九丘查询    🏢 SPOS 查询
```

**期望展示**（✅ 按平台分组）：

```
▼ 已接入平台（3 个平台 · 共 N 个接口）
  ┌─ 服务云 ──────────────────────┐
  │  🔍 服务云查询                  │
  │  ... (未来可能有更多接口)        │
  └────────────────────────────────┘
  ┌─ 九丘 ────────────────────────┐
  │  🔍 九丘查询                    │
  └────────────────────────────────┘
  ┌─ SPOS ────────────────────────┐
  │  🔍 SPOS 查询                  │
  └────────────────────────────────┘
```

**分析与解答**：

当前 `NodeDefinition` 的 `type` 字段已经采用了 `domain.action` 的命名约定（如 `serviceforce.query`、`jiuqiu.query`、`spos.query`），可以直接用 `.` 前面的部分（domain）作为平台分组依据。

但目前数据模型里缺少一个显式的 **平台信息** 字段。需要的改动：

1. **数据模型扩展**：在 `NodeDefinition` 或 `NodeMetadata` 中增加 `platform` 字段（或者用 `type` 的 domain 部分推导）：
   ```typescript
   // 方案 A：显式字段（推荐）
   interface NodeDefinition {
     platform?: string;        // "serviceforce" | "jiuqiu" | "spos" | ...
     platform_label?: string;  // "服务云" | "九丘" | "SPOS" | ...
     // ... 其余字段
   }
   
   // 方案 B：从 type 推导（零改动，但灵活性低）
   const platform = node.type.split('.')[0]; // "serviceforce"
   ```

2. **前端分组逻辑**：`NodeMarket.vue` 中 connector 分组需要二级嵌套——先按 platform 分组，再列出每个平台下的节点。

3. **平台元信息**：需要一份"平台注册表"（平台名 → 图标 / 中文名 / 描述），可以硬编码在前端或存为 `data/platforms.json`。

**后续优化方向**：

- [ ] 在 `NodeDefinition` 中增加 `platform` / `platform_label` 字段
- [ ] 更新已有的 connector JSON 数据文件，补充平台信息
- [ ] 前端 `NodeMarket.vue` 改为二级分组渲染
- [ ] 可选：增加 `data/platforms.json` 平台注册表
