### 问题 17：基于成熟开源平台二开的二期路线洞察

**问题描述**：

当前项目不是要在第一阶段完整复刻一个成熟工作流平台，而是通过 demo 呈现我们的核心主张：

- 企业内部存在大量“可被自动化但缺少标准 API 产品化”的业务系统操作。
- 通过真实浏览器/接口录制，可以把这些业务操作沉淀成可复用的系统工具、插件或节点。
- 通过模型理解用户意图和节点能力，可以自动编排出面向业务场景的工作流。
- 业务人员不需要从零学习复杂编排平台，就能从“描述需求”走到“可试运行的流程”。

在这个主张被 demo 证明后，必须正视一个问题：完整工作流平台的工程化建设成本很高。画布、节点编辑、连线、调试、权限、发布、日志、版本、插件生态、团队协作等能力，不应全部由当前 demo 从零自研。

因此，本主题作为后续说服老板和规划二期的重要洞察：一期 demo 用最小成本证明核心价值；二期应站在成熟开源平台的肩膀上，通过本地化和二次开发补齐平台能力，把研发重点放回我们的差异化能力。

**当前态**：

一期 demo 已初步证明的核心能力：

- 录制接口：通过真实浏览器/接口录制，把企业系统操作转成可调用节点。
- 节点市场：让录制结果具备名称、输入、输出、平台归属和复用入口。
- 新建工作流：用 LLM 根据自然语言和节点能力生成可执行 workflow。
- 试运行闭环：支持校验、卡片预览、节点输入输出快照和最终结构化结果。
- SOP1 验证样例：围绕直客订单，实现“工单查询 → 多源信息汇总 → 场景判断 → 邮件草稿”的业务链路。

同时，一期 demo 的不足也很明确：

- 工作流视图和节点关系展示仍是 demo 级，不是成熟画布。
- 节点配置、版本管理、复杂调试、权限、发布、团队协作都还很轻。
- 继续自研平台能力会消耗大量时间，且这些能力不是我们的核心差异化。
- 一期真正有价值的是“企业系统操作录制成工具”和“AI 自动编排工作流”，而不是重新造一个 FastGPT/n8n。

**期望态（用于老板沟通）**：

对外/对上沟通时，可把项目分成两层价值：

1. 一期 demo 证明核心主张
   - 我们不是先做一个大而全平台，而是先用 SOP1 证明：
     - 企业系统操作可以被录制为工具。
     - 工具可以被结构化描述、校验、试运行。
     - AI 可以基于业务需求自动编排流程。
     - 业务结果可以结构化输出，并触发后续处理。

2. 二期站在成熟平台上放大价值
   - 选择 FastGPT 等成熟开源 AI 工作流平台作为底座候选。
   - 复用其工作流画布、节点体系、调试日志、插件/MCP、发布和应用管理能力。
   - 我们专注做平台缺少或企业场景更关键的能力：
     - 企业系统接口/页面录制。
     - 录制结果自动转工具/插件/MCP。
     - 面向业务 SOP 的 AI 工作流生成。
     - 企业登录态、权限、内网系统和回放稳定性。

**分析与解决**：

#### A. 关键洞察

FastGPT 这类平台已经证明了“AI 应用 + 可视化工作流 + 工具/插件生态”的产品形态是成立的。FastGPT 当前公开能力包括 Flow 可视化工作流、节点输入输出、条件/并行/HTTP/代码运行、工具调用、MCP 工具集和系统插件等。

这说明我们不需要从零证明“工作流平台”本身成立。我们要证明的是：

- 企业内部系统的操作可以低成本沉淀为工具。
- AI 不只是调用一个工具，而是能围绕业务 SOP 自动组织多工具流程。
- 录制工具 + AI 编排，可以显著降低企业自动化落地门槛。

换句话说，成熟平台解决的是“工作流基础设施”；我们的创新点解决的是“企业工具生产”和“业务流程自动生成”。

#### B. 当前 demo 的战略价值

当前 demo 仍然值得继续做，因为它承担的是验证和说服作用：

- 证明 SOP1 这类真实业务流程可以从自然语言描述进入可执行链路。
- 证明录制节点可以作为企业工具资产沉淀，而不是一次性脚本。
- 证明结构化输出、场景判断、邮件草稿等能力能闭环一个业务 case。
- 让老板和业务方看到“最终会变成什么”，而不是只听一个平台化愿景。

因此，一期 demo 的目标不是工程完美，而是清晰表达理念：

> 业务人员描述需求，系统自动识别可用企业工具，生成可试运行的 SOP 工作流，并输出结构化结果和后续动作。

#### C. 为什么二期不宜继续完全自研

如果继续自研完整平台，后续会出现明显成本：

- 画布与交互成本：拖拽、连线、节点布局、缩放、选择、快捷操作。
- 编排能力成本：复杂 DAG、并行、循环、分支、人工节点、异常策略。
- 调试成本：节点日志、变量快照、重跑、断点、历史版本、运行对比。
- 平台成本：账号、权限、团队空间、发布、分享、模板市场。
- 生态成本：插件规范、系统工具、MCP、第三方工具接入。

这些能力很重要，但不是我们最应该投入的差异化方向。站在成熟开源平台上，可以把这些通用平台能力作为底座，把有限研发资源集中到“企业系统录制”和“AI 编排”。

#### D. FastGPT 作为二期底座候选的匹配度

1. 录制接口 → 工具/插件/节点
   - 我们录制出来的节点，本质上就是一个有输入、输出、执行器的系统工具。
   - 可以通过三种方式接入 FastGPT：
     - HTTP 节点调用我们的录制节点执行 API。
     - 将录制节点服务包装为 MCP Server，通过 FastGPT MCP 工具集接入。
     - 生成 FastGPT 系统插件/工具定义，作为更深度二开方向。

2. 新建工作流 → AI 生成平台工作流
   - FastGPT 已有可视化工作流，二期可以不再生成自研 YAML，而是生成 FastGPT workflow JSON。
   - 我们的差异化从“自研 runner”转为“LLM workflow compiler”：
     - 输入：用户需求、可用录制工具、业务 SOP 规则。
     - 输出：FastGPT 可导入/保存/运行的 workflow。

3. SOP1 → PoC 验证样例
   - SOP1 可以作为二期 PoC：
     - 服务云录制工具。
     - 九丘录制工具。
     - SPOS 录制工具。
     - 结构化汇总节点。
     - R1-R6 场景判断。
     - 邮件草稿动作。
   - 如果这个链路能在 FastGPT 上跑通，就说明“开源平台底座 + 我们的录制/AI 编排层”路线成立。

#### E. 风险与边界

- FastGPT 不是轻量库，而是成熟平台；本地化、理解数据模型和二开需要成本。
- FastGPT license 是 Apache 2.0 加附加条件；如果未来做类似多租户 SaaS、移除或修改品牌信息，需要提前确认授权。
- 不建议一开始深度 fork 工作流核心。优先用 HTTP/MCP/插件方式接入，降低跟随上游升级的成本。
- AI 生成 FastGPT workflow 的可行性要通过 PoC 验证，重点看 workflow JSON 是否稳定、是否有导入/保存 API、校验是否可控。
- 企业系统登录态、内网访问、浏览器回放等仍可能需要我们自己的执行服务承载，不能假设 FastGPT 原生 HTTP/沙盒节点就能解决。

#### F. 二期建议路线

建议把二期规划为“三层架构”：

1. 工作流平台底座
   - 候选：FastGPT 本地化部署和二开。
   - 负责：画布、节点关系、运行日志、调试、应用发布、插件/MCP 生态。

2. 企业工具生产层
   - 来源：当前录制接口能力。
   - 负责：录制企业系统操作、提取输入输出 schema、生成工具定义、维护登录态和回放执行。

3. AI 工作流编排层
   - 来源：当前新建工作流能力。
   - 负责：根据自然语言需求和可用工具，生成平台可执行工作流；做结构校验、引用校验、试运行修正。

推荐二期 PoC 顺序：

1. 本地部署 FastGPT，确认 license 和部署成本。
2. 用 HTTP 节点调用一个当前录制节点 API，跑通最小工具调用。
3. 尝试将录制节点服务包装成 MCP Server，并通过 FastGPT MCP 工具集接入。
4. 手工在 FastGPT 中搭建 SOP1 最小工作流，验证并行、条件、结构化输出和邮件草稿动作。
5. 导出或读取 FastGPT workflow JSON，分析其 schema。
6. 让 LLM 生成 FastGPT workflow JSON，验证导入、校验、试运行闭环。
7. 根据 PoC 决定是否把 FastGPT 作为二期正式底座。

#### G. 对老板的建议表达

可以这样讲：

> 一期我们不是要从零做一个完整工作流平台，而是用 demo 证明企业 AI 自动化的核心突破点：把企业系统操作录制成工具，再让 AI 自动编排成业务流程。这个 demo 能证明价值，但如果继续把画布、调试、权限、发布、插件生态都自研，会进入高成本平台建设。二期我们建议站在 FastGPT 这类成熟开源 AI 工作流平台上做本地化二开，把通用平台能力交给成熟底座，把我们的研发重点集中在企业工具录制和 AI 自动编排这两个差异化能力上。
