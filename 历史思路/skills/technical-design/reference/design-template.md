# design.md 模板 · Architecture + Solution

> 落盘位置: `openspec/changes/<topic>/design.md`
>
> 本模板按「原则 -> Architecture -> Solution」组织。原则用于约束判断，最终产物主体是 Architecture 和 Solution。

```markdown
# <Topic Title> · Technical Design

## 元信息

- **关联 proposal**: `openspec/changes/<topic>/proposal.md`
- **关联 spec**: `openspec/changes/<topic>/specs/spec.md`
- **模式**: incremental / from-scratch
- **状态**: draft / approved

## 背景与硬约束

<一段话说明本 design 服务哪个目标。只写会影响 Architecture 或 Solution 的硬约束：性能、规模、合规、deadline、人员能力、业务优先级等。>

## 设计原则应用

- **约束先于偏好**: <本 design 中最重要的硬约束是什么>
- **尊重现状 / 克制扩展**: <incremental 如何尊重现状；from-scratch 如何避免过早抽象>
- **边界清楚，可改可测**: <如何让变化集中、接口稳定、测试可达>
- **决策可追溯**: <关键决策如何关联 User Story 或硬约束>

## Architecture

Architecture 说明系统如何组织。

### 与现有架构的关系

> incremental mode 必填；from-scratch 写「无既有架构」。

- **涉及的现有模块**: <列举>
- **沿用的接口 / 领域词汇**: <列举>
- **相关既有设计约束**: <只列项目内已经明确存在、且与本 topic 直接相关的约束>
- **兼容性影响**: <谁会受影响，是否需要迁移，是否破坏向前/向后兼容>

### 模块与边界

| 模块 | 职责 | 边界 | 依赖 | 变化归宿 |
|---|---|---|---|---|
| `<模块名>` | <做什么> | <负责什么，不负责什么> | <依赖谁> | <哪些变化会落到这里> |

### 接口 / 契约

- **调用方式**: <调用方如何使用>
- **数据格式**: <跨模块或外部接口的稳定格式>
- **不变量**: <必须始终成立的规则>
- **错误语义**: <失败、重复、重试、幂等、降级等语义>
- **顺序 / 一致性保证**: <需要时填写>

### 关键数据流

1. <输入 / 触发>
2. <经过哪些模块>
3. <产生什么状态变化、副作用或输出>

### 架构质量说明

- **可维护性**: <模块是否能独立理解和测试，变化是否集中>
- **可扩展性**: <保留哪些扩展点，依据是什么；明确不保留哪些假想扩展>
- **测试可达性**: <关键行为如何验证>

## Solution

Solution 说明需求如何被解决。

### 核心解决策略

<用什么机制满足主要 User Stories。>

### 关键流程

1. <触发条件>
2. <处理步骤>
3. <输出 / 状态变化>

### 数据处理策略

- **生成**: <关键数据如何生成>
- **校验**: <如何保证合法性>
- **转换 / 同步 / 回写**: <需要时填写>
- **存储或持久化**: <需要时填写>

### 异常与兼容策略

- **失败处理**: <失败如何暴露、回滚、重试或降级>
- **重复 / 边界情况**: <重复提交、空数据、极端输入等如何处理>
- **兼容影响**: <对已有行为、已有数据或已有入口的影响>

### 技术选型与取舍

只列对架构、数据契约、部署、测试、性能、合规或长期维护有影响的选型。

| 决策点 | 选择 | 备选 | 理由 | Trade-off | 关联 |
|---|---|---|---|---|---|
| <例：持久化方案> | <X> | <Y/Z> | <为什么选 X> | <付出什么代价> | User Story # / 约束 |

### 风险与验证

| 风险 / 假设 | 影响 | 缓解 / 验证方式 | 决议时点 |
|---|---|---|---|
| <风险> | <影响范围> | <实验验证 / 测试 / 人工确认> | <本阶段 / 实施计划 / 开发实现 / 测试验收> |

### 约束满足方式

- **性能 / 规模**: <如何满足>
- **合规 / 安全**: <如何满足>
- **deadline / 人员能力**: <如何满足>
- **其他硬约束**: <需要时填写>

## 回填到 spec.md 的 Implementation Decisions

> 将本段精简复制到 `specs/spec.md` 的 `Implementation Decisions`。只保留与 User Stories 或硬约束直接相关的决策。

- **User Story #<编号>**: <采用的关键实现决策>
- **约束：<名称>**: <满足方式>

## 不在本阶段处理

- **下一阶段实施计划**: 具体任务拆分、文件级步骤、测试用例编号、提交顺序
- **开发实现**: 具体代码、函数体、局部实现细节
- **测试验收**: 完整测试断言、测试数据矩阵、发布检查清单
```
