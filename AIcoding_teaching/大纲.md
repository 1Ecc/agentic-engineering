# AI coding 培训总框架（1 小时）

> 面向研发 / 业务 / 产品管理的普适性培训。目标不是教某个工具按钮怎么点，而是让大家理解 agent / AI coding 的本质，并学会在真实业务里把 agent 管好、用好、沉淀成复利。

## 0. 为什么需要这场培训

真实业务里，越来越多非技术同事已经开始尝试用 AI coding / agent 化来解决问题：整理资料、生成脚本、分析数据、搭建小工具、自动化流程、辅助产品和运营决策。

但当前最大的问题不是「大家不会打开工具」，而是认知模糊：

1. **agent 是什么**：它和普通聊天、脚本、自动化工具有什么区别？
2. **AI coding 是什么**：这里的 coding 不是所有人都要写代码，而是把问题表达成可执行、可验证、可迭代的任务。
3. **它能解决什么问题**：哪些适合交给 agent，哪些不适合，边界在哪里？
4. **为什么结果经常不好用**：需求没对齐、上下文乱、文件和记忆管理差、没有验证、后期不可维护。
5. **怎么把一次成功变成复利**：把提示词、流程、文件结构、测试、经验沉淀成团队可复用资产。

所以这场培训的核心不是「炫技」，而是补齐共同语言：让非技术人员敢用、会提需求、会验收；让技术人员知道怎么把 agent 放进工程流程；让产品和管理者理解边界、风险和推广路径。

## 1. 培训目标与听众

**培训目标**

1. 让所有人用大白话理解：AI coding / agent 到底是什么。
2. 解释可以用什么工具，以及为什么需要 Codex、Claude Code、WorkBuddy 这类 agent 平台。
3. 讲清楚 AI coding 的核心不是「人去 coding」，而是人如何管理 agent 做事。
4. 引出 agentic engineering：需求对齐、文件管理、记忆管理、验证、可维护性和复利沉淀。
5. 给出后续能做的事情、建议和小技巧，让听众离场后能立刻尝试。

**听众差异**

| 人群 | 关心什么 | 培训中给到什么 |
|------|----------|----------------|
| 研发人员 | 原理、工具链、质量、安全、怎么落进代码库 | agent 循环、上下文、skills/MCP、SDD+TDD、验证与维护 |
| 业务人员 | 能帮我做什么、怎么沟通、怎么验收 | 从业务问题到任务说明、边界、验收标准、可复用模板 |
| 产品/管理人员 | 效率、流程、风险、团队怎么推广 | 工程化平台、权限与成本、团队工作流、复利沉淀 |

## 2. 主题一：agent / AI coding 的本质（约 20 分钟）

**核心问题**：agent 是什么？AI coding 到底在 code 什么？

**一句话主线**

> agent = 大模型 + 一个循环 + 执行命令 + 一份说明书（提示词 / 技能）

**结构**

1. Chat 引子：大家每天用的对话框，本质是模型 API 的外壳。
2. 单次 API：模型先是一个问答函数。
3. 多轮无记忆：它不是失忆，是你没把上文喂给它。
4. 多轮有记忆：记忆 = 每轮把历史 messages 再喂一遍。
5. Agent 化：system 说明书 + 命令执行 + 循环。
6. Skill / MCP：模型不会的能力，要么写成说明书，要么接外部工具。
7. 网页/手机壳：所谓 openclaw，只是同一个 agent 循环外面套了更易用的界面。

**本章落点**

- 对非技术人员：AI coding 不是让你变程序员，而是把业务问题转成 agent 能执行的任务。
- 对技术人员：agent 不神秘，真正关键的是循环、上下文、工具、权限和反馈。
- 对所有人：模型能干多少，取决于你喂给它什么，以及你如何让它验证结果。

**材料位置**

- 讲解脚本：`coding本质/讲解设计.md`
- 证据与收尾：`coding本质/为什么需要agent平台.md`
- 可运行 demo：`coding本质/demo/`

## 3. 主题二：可以用什么工具，为什么需要 agent 平台（约 12 分钟）

**核心问题**：既然 20 行能写 agent，为什么还要 Codex / Claude Code / WorkBuddy？

**讲法**

1. 从第一章自然暴露的问题进入：越喂越多、越跑越危险、越复杂越不稳定。
2. 把问题归纳成三类：
   - 上下文管理：喂什么、什么时候喂、怎么压缩、怎么检索。
   - 工具与能力管理：skills / MCP / 插件如何加载、调度、隔离。
   - 工程安全与质量：权限、沙箱、测试、回滚、审查。
3. 给出概念：Agent = Model + Harness；把 harness 做好就是 harness engineering。
4. 介绍工具地图：通用聊天工具、AI IDE、命令行 agent、企业平台、内部插件/skills。

**关键概念**

| 概念 | 本质 | 培训落点 |
|------|------|----------|
| Skill | 操作说明书 | 教模型怎么用已有命令 / 流程 |
| MCP | 外部能力标准接口 | 给模型接数据库、GitHub、搜索、内部系统 |
| 插件 | 打包分发单元 | 团队能力的一键安装与复用 |
| 上下文管理 | 控制喂给模型的信息 | 同时影响价格、质量、时间 |
| Harness | 模型外面的工程壳 | 决定 agent 是否能稳定做事 |

**本章落点**

- 工具不是越多越好，而是要看谁在帮你管理上下文、工具、权限、验证和协作。
- 对非技术人员，agent 平台降低的是「把业务问题变成可执行任务」的门槛。
- 对技术人员，agent 平台提供的是工程化 harness，而不是替代软件工程常识。

## 4. 主题三：如何管理 agent，引出 agentic engineering（约 18 分钟）

**核心问题**：AI coding 的核心不是我们自己 coding，而是如何管理 agent 把事情做对、做好、做得可持续。

真实使用中一定会碰到这些问题：

1. **怎么沟通**：我该怎么描述任务，agent 才不会误解？
2. **怎么对齐需求**：如何确认「它理解的需求」就是「我真正想要的需求」？
3. **怎么做好文件管理**：材料、代码、输出、记录放哪里，下一轮还能接上吗？
4. **怎么做好记忆管理**：哪些信息要写进 `AGENTS.md`、handoff、spec、README，哪些只留在聊天里？
5. **为什么做出来不好用**：没有验收标准、没有测试、没有真实场景反馈。
6. **为什么后期维护性低**：一次性提示词太多，缺少结构、规范、测试和交接。
7. **怎么增加复利**：把一次有效做法沉淀成模板、skill、插件、检查清单、团队规范。

**本仓方法论落点**

> SDD 管「做什么」，TDD 管「怎么做对」。

**建议讲解框架**

1. S0：Bootstrap
   - 建立任务入口、项目规则、约束、可用工具。
   - 对应材料：`AGENTS.md` / `CLAUDE.md` / 项目 handoff。
2. S1：Main Loop
   - 需求澄清 → spec → plan → implement → verify → handoff。
   - 强调人负责目标与判断，agent 负责执行与反馈。
3. S2：Scale
   - skills、模板、测试、review、CI，把个人经验沉淀为团队能力。

**贯穿 case（现场用本仓 `ae` 造一个产品）**

选定任务：**现场开发「Knode v0」——一个团队内部的 skills hub**（本地 skills 同步 + 广场浏览 + 搜索/详情/下载 + 轻量安全徽章）。**形态为稳定性而定：纯前端 + 只读轻量服务**（同步脚本 + `python -m http.server`），不写盘、不建库。一个真实但模糊的产品需求，现场跑 S0→S1→S2：

1. `ae setup` / `ae init` 立项目骨架（S0）。
2. 打一句模糊需求，**先让 agent 反问对齐 + 砍范围**（哪些板块做、下载写不写盘、上传做不做），产出 `prd.md`（A1→A2）。
3. 生成 `design.md` / `todo.md`，拆成 4–5 步（A3→A4）。
4. **TDD**（纯函数）：先写测试再实现，先红后绿——同步解析 / 去重 / 搜索 / 安全徽章（A5）。
5. 起静态服务器、**当场打开网页**验收：本地+广场列出 → 搜 `email` → 切「集团」过滤 → 下载加清单 → 风险节点带徽章（A6）。
6. 写 handoff——**你刚跑出来的就是 Knode 雏形**，直接交棒第四章。

> 刻意选成 **第四章 Knode 的雏形**；本地同步的就是 `ae setup` 刚装的 skill，广场第一条就是已沉淀的 `skills/powerautomate-email-to-sharepoint-excel`。
> 完整剧本 + 道具：`管理agent的工程方法/`（`讲解设计.md` + `demo/plaza_nodes.json` + `demo/产品说明_v0.md`）。

**跨人群翻译**

| 工程词 | 给非研发的说法 |
|--------|----------------|
| spec | 先把「要什么」说清楚 |
| test | 先定义「怎样算做对」 |
| review | 让另一个视角检查风险 |
| handoff | 把当前状态写下来，下一轮能接上 |
| skill | 把优秀员工的 SOP 写成可复用卡片 |

## 5. 主题四：节点复用与知识复利（约 10 分钟，**全场价值高点**）

**核心问题**：这件事对我们组织到底意味着什么？能不能从中长出一门新生意？

**一句主张**

> 不同业务任务，底层「节点」高度重复；把节点标准化、沉淀下来，就能换来 **技术平权 + 知识复利**——这本身可能是一门新生意。

**四段式（讲故事）**

1. **发现**：四个完全不同的真实需求（手机发板 / ThinkBook 驱动 / 知识库批更 / CES 智能体知识导出），拆开看是**同一批节点的重新排列组合**（邮件采集 / 平台取文件包 / 批量导出 / 接口补字段 / 整理转换 / 知识发布）；而「看似最简单」的节点（如邮件采集）藏着最多坑。
2. **我的想法**：两根支柱——① 技术平权 + 标准化 → 协同；② 知识流沉淀 + 复利。**它们正好就是前三章那套方法（spec / skill / handoff / S2）放大到组织尺度。**
3. **可拓展性**：复利阶梯——个人 → 团队 → 组织共享平台 → 对外方法论产品。
4. **新业务机会（产品暂名 Knode = knowledge + node）**：节点级复用、沉淀决策与弯路、用 spec/skill 做契约；从最痛节点切入，护城河是复利/网络效应；并诚实给出风险边界。

**真实素材（仓库里就有）**

- `skills/powerautomate-email-to-sharepoint-excel`：已沉淀的「邮件抓取」踩坑节点——「沉淀 → 复利」活的证据。
- 第三章现场产出的「格式整理」节点，与它并排组成节点库雏形。

> 完整专题（叙事骨架 + 配图建议 + 待补槽位）：`节点复用与知识复利/讲解设计.md`。
> 需求框架 / 案例细节 / 平台形态由你后续补充。

**收场前的小技巧（30 秒带过即可）**

1. 别让 agent「直接做」，先让它复述需求和验收标准。
2. 大任务拆小，每步要可检查的产出。
3. 重要背景写进文件，别只留在聊天窗口。
4. 关键结果要验证：测试 / 样例 / 截图 / 人工清单。
5. 有用的做法别私藏——沉淀成团队资产，才有复利。

> 说明：主题四拔高为价值高点后，总盘重新配平到 60 分钟；主题一/三按现场弹性压缩。

| 模块 | 时间 | 目标 |
|------|------|------|
| 开场：为什么需要这场培训 | 5 min | 对齐真实业务动机：大家都想用 agent，但概念、边界和方法模糊 |
