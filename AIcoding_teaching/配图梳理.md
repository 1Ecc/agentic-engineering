# AI coding 培训配图梳理

> 目标：为四个主题各准备一张主图。当前文件先沉淀配图底稿，后续逐一优化细节，最终调用 image2 生图。

## 总体原则

- **一章一主图**：每张图只承担一个核心认知，不把所有概念都塞进同一张图。**例外：第三章原图 3 太满，拆成图 3a（痛点+巨人+设计思路·WHY）和图 3b（架构·WHAT）两页；第四章原图 4 同理，拆成图 4a（发现·重复节点矩阵）和图 4b（怎么做出复利·两列）。**
- **中文标签清晰**：图中只放短标签，详细解释留给口播。
- **从机制到价值递进**：图 1 讲本质，图 2 讲平台必要性，图 3（拆 3a/3b）讲管理方法，图 4（拆 4a/4b）讲组织复利。
- **同一视觉体系**：扁平科技风、白底或浅色底、线条清晰、少装饰、适合放进 PPT。
- **先结构后美术**：后续先确认每张图的信息结构，再交给 image2 出正式图。

## 图 1：agent 平台的本质

**对应主题**：`AIcoding_teaching/agent平台的本质`

**背景（这张图为什么存在）**

> 大家都在用 AI coding / agent 平台，却说不清它**能做什么、又是怎么做到的**。这张图从最熟悉的 ChatGPT 出发，按「撞到问题 → 补一块能力」的演进，一步步把 agent 平台拆开——看清本质，顺手回答「能做什么、怎么做」。

**一句话**

> agent 平台不神秘：从最熟悉的 LLM 问答（ChatGPT / 豆包）起步，换成 AI coding 里真正用的「API 接口」，再每撞到一堵墙就补一块能力——循环+历史（记忆）→ 命令执行（agent）→ skills/mcp（专长）→ 平台壳（openclaw）。最外层那只「龙虾」就是这么长出来的。

**要表达的关系（问题驱动的演进 · 6 个 step / 4 拍）**

```text
【起点】最初的 LLM 大模型：平时你用 ChatGPT / 豆包「问答」（网页 / App）
        到了 AI coding：在代码里 / 调用节点里改用「API 接口」
        问题：API 一上来只能单轮、没记忆
           ↓ 加 while 循环 + 每轮把历史 messages 再喂一遍
  ① 多轮对话 ≈ 现在的 chatbot        →（引出：记忆）

        问题：怎么让 LLM 真正「干活」？
           ↓ 给 system 说明书 + 让它执行命令 + 循环
  ② Agent：能读写文件 / 跑命令        →（引出：AGENTS.md / system prompt）
                                       （顺手回答：agent 能做什么、怎么做的）

        问题：特定领域 / 特定工作它不会做？
           ↓ 提前把「该怎么做」补给它
  ③ skills + mcp                      →（引出：skills / mcp）

        问题：大家熟知的 openclaw 又是怎么弄出来的？
           ↓ 在这套循环外面套一层工程化平台壳
  ④ openclaw / codex / claude code    →（引出：agent 平台）

【收尾 · 衔接主题 2】
  既然几十行就能搭出 agent，为什么还要用这些平台？
  （它越喂越多、越跑越危险、越复杂越不稳——谁来替我管？）  →  主题 2
```

**建议画法（抽象逻辑 · 一个「用户」的闯关之旅）**

不画技术框图，改用**一个用户小人沿路前进**来表达：每到一站**先冒出一个烦恼**（皱眉 / 抓头 + 吐槽气泡），**补上一块能力**后**松一口气**，再走向下一个烦恼。用「表情 + 气泡」讲逻辑。

- **起点**：用户在 `ChatGPT / 豆包` 前轻松**问答**（😀）。一转身做 AI coding，得改用 **`API 接口`** 在代码 / 工作流里调模型。
- **第①站（麻烦）**：API 一问一答，**每次都要手动重新发起，太麻烦**（😣）→ 给它套一个 **`循环`**。
- **第②站（苦恼）**：循环连上了，可**它不记得我上一句问了啥**（😖）→ 把 **`历史 messages`** 一起喂回去（= **记忆**）→ 这下像 `chatbot` 了。
- **第③站（苦恼）**：想让它**帮忙干点活**，它却**只会回文字、不动手**（😩）→ 加 **`命令执行` + 说明书 `AGENTS.md`** → 升级成 **`Agent`**，能读写文件 / 跑命令。
- **第④站（卡住）**：**我本职的专业活 / 特定场景它不会做**（😵）→ 给它 **`skills` 说明书**、接 **`mcp` 外部能力**。
- **终点**：把这一整套套进平台壳 → **`openclaw / codex / claude code`**。
- 颜色：问答区暖色，进入 agent / skills / 平台后转冷色。**结尾仍放一张问号卡片**：「既然自己就能一步步搭出来，为什么还要平台？」→ 主题 2（别停在「平台壳」就收尾）。

**口播落点**

- 大家平时用 ChatGPT / 豆包问答；可一做 AI coding，就得改用 API 接口在代码里调模型。
- 一开始一问一答、每次都手动重发，**太麻烦** → 套个循环让它自动连着问。

- 最后把这一整套套上平台壳，就是大家说的 openclaw。

## 图 2：为什么需要 agent 平台

**对应主题**：`AIcoding_teaching/为什么需要agent平台`

**背景（这张图的矛盾，开场就抛）**

> 第一章你亲手看到：**几十行就能搭出 agent，甚至 openclaw**。那为什么还要用 Claude Code / Codex？
> 钩子：2026 年 3 月底，Claude Code 的打包源码被社区反编译——「几十行能跑的东西」，真身是**几十万行量级的工程**（光明文字符串就 14 万+条，系统提示 / 工具描述 / 行为指令全在里面；其实它一直随 npm 包发出来，是 minify 不是加密）。**那多出来的几十万行，到底在干什么？答案就是 harness。**

**一句话**

> Agent = Model + Harness。模型谁都能调；**几十行 → 几十万行**的差距，全是平台替你做的工程壳——上下文、能力、规划、安全。

**要表达的关系（矛盾 → 痛点 → harness 四块 → 上手）**

```text
【矛盾】几十行就能跑的 agent ——凭什么 Claude Code 要写成几十万行？
        （3 月底源码被反编译：14 万+明文字符串全是工程细节）
   ↓ 从第一章的演进，痛点自己冒出来
【痛点】① 上下文越喂越多 → 贵 / 慢 / 质量下降（窗口有限 + 注意力有限 = context rot）
        ② 越跑越危险      → agent 手握 终端 / 文件 / 命令行 / 浏览器，却没护栏
        ③ 工具越加越乱    → 加载、调度、生态差，能力互相打架
   ↓ 那几十万行，就是来解决这三件事的
【harness 四块工程化能力】
   ① 上下文管理   长短期记忆 · 基础设定 · 外部知识 · 自动压缩阶梯
   ② 能力接入     tools/function calling · MCP · skills · cli/shell · plugin（可插拔可分发）
   ③ 规划与调度   任务拆解 · plan · subagent · 反馈自纠
   ④ 安全与权限   分级权限 · 沙箱（默认无网 / 限工作区）· 越界才审批
   ↓
【快速上手】
   Claude Code / Codex
   无订阅：cc switch 接国产模型 API
   选型：GLM-5.2 = Coding 最强 · DeepSeek V4 Pro = 世界知识最强
```

**（建议补图）图2b · 上下文管理机制阶梯**

> 「上下文管理」是 harness 里最值钱、最有料的一块，单独出一张「压缩阶梯」图把它讲透。

- 先放**典型请求结构**，让人直观看到「为什么会爆窗」：
  `system prompt ~5k + 项目说明 AGENTS.md ~10k + skills 定义 ~20k + tool/mcp 定义 ~30k + 历史会话 ~100k + 代码文件 ~50k + 用户问题 ~0.1k ≈ 215k`，轻松撑爆 200k 窗口。
- 再放管理对象（四类）：**短期记忆**（当前会话，会被压）/ **长期记忆**（跨会话：CLAUDE.md、memory tool）/ **基础设定**（system、入口规则）/ **外部知识**（按需检索，只存路径用时再读）。
- 核心是 claude code 的**四档压缩阶梯**（越往下越「重」，正是「几十万行」在干的活）：
  1. **日常清理（无感、不花钱）**：micro-compact 本地裁掉旧工具结果（无 API、保护最近窗口与最近 3 条）；API 原生 context editing 服务端清洗旧结果。
  2. **主动摘要（花一次 API）**：auto-compact 接近上限时生成结构化摘要替换历史（预留约 13k 缓冲、摘要 ≤ 约 20k）；context collapse 分段折叠。
  3. **用户主动**：`/compact` 手动压缩（可带指令）· `/clear` 清空但留代码 · `/btw` 支线快问不污染主线 · `/rewind` 回退。
  4. **兜底防御**：reactive compact 撞「Prompt Too Long(413)」时紧急压缩（只留最近几条、一次重试）；snip 强裁超大块内容。
- 图注：机制名来自社区对 claude code 打包源码的反编译；**阈值随版本 / 模型变动**，口播统一说「接近上限自动压缩」。建议 **SVG**（堆叠条 + 阶梯，生成式画不准数字）。

## 图 3a：从混乱协作，到工程化编排（失控现场 → 参考蓝图墙 → 工程蓝图）

**对应主题**：`AIcoding_teaching/管理agent的工程方法`（上半 · WHY）

> **定调（2026-06-21 更新）**：3a 只负责把 **agentic engineering** 引出来，不讲完整架构。呈现形式改成**故事图**：左边是 AI coding 常见失控现场，中间是市面上高 star / 好用方法的**参考蓝图墙**，右边是我们基于自身工程经验做的**工程蓝图**：`SDD + TDD + 软件生命周期节点 skills`。**3b 接着讲 WHAT（这套方法如何落进过程节点和项目骨架）。**

**背景（这张图为什么存在）**

> AI coding 的核心问题，不是 agent 不会写代码，而是**开发全生命周期没人管**：需求、状态、验证、维护、沉淀都可能断。市面上已经有不少高 star / 好用的方法，我们不是重复造轮子，而是复用它们的强项，再按自己的工程约束组合成一套轻量闭环。

**一句话**

> AI coding 的常见事故逼出工程方法论；高 star 方法各管一段，我们把可复用的部分重新组合：**SDD 管做什么，TDD 管做得对，软件生命周期节点 skills 管怎么执行和沉淀**。

**口播落点**

- AI coding 的问题不是模型不会写代码，而是你不管理它，它就会把需求、状态、测试、维护和沉淀这些工程环节都打散。

## 图 4b：怎么提高复利 —— 一个节点的踩坑，怎么滚成全组织的复利

**对应主题**：`AIcoding_teaching/节点复用与知识复利`（下半 · 怎么做出复利）

> **定调（2026-06-21 更新）**：改成**故事插画**，围绕一个 case：`获取 Outlook 邮件`。左边 = “我”从实现这个功能开始，连续踩坑，最后沉淀出一条**知识流**；右边 = 这条知识流怎么从个人复用，扩散到团队公共区、集团平台 **Knode**，最后变成可对外拓展的产品能力。`skill` 不再是主概念，改为知识流的一种落地形态；小字补 `skill / DRA / MCP 等`。
