## 1. 当前实现与本轮范围

当前 `src/skeleton.js` 固定创建 `spec/`、`reference/`、`data/`、`scripts/` 及占位文件。README 模板把运行产物、导出、缓存一起归入 `data/`。根 AGENTS.md 发布模板仍只有标题与目标。

现有 `writing-plans` 的 File Structure 已要求明确文件职责、接口边界,把一起变化的文件放一起。持续治理还需要覆盖不进入 S1 的快修、脚本,且不能只依靠初始化时的空目录。

本轮明确的用户偏好:

- 新项目默认仅用 `src/` 承载手写实现与脚本,不再单列 `scripts/`。
- 保留 `tests/`。
- 原始文档资料纳入 `docs/`,暂不为外部参考代码设计独立 `reference/`。
- 保留 `docs/`,构建产物统一优先使用 `dist/`。
- 数据与运行结果统一归入 `data/`,内部结构由具体项目按渐进组织、渐进披露原则决定。
- spec 与源码不强制一一对应;已有合理的框架布局不强行更名。
- 通过根 AGENTS.md 的一条通用规则覆盖目录组织,不默认增加 `src/AGENTS.md` 等同义规则文件。

用户检查后已要求开始执行。本仓骨架实现、发布模板与相关文档已按下文更新;测试、打包、npm 与 Git 发布结果在收口时记录。

## 2. 收敛后的标准目录

| 目录 | 职责 | 内部组织 |
|------|------|----------|
| `spec/` | 需求、设计、验收与 ADR | 沿用现有专门规范 |
| `src/` | 业务实现、程序入口及辅助脚本 | 按稳定能力/职责聚合,共同变化的实现尽量靠近 |
| `tests/` | 行为测试与测试样例 | 按被验证的能力或测试场景分组;不强制每个源码文件配一个测试文件 |
| `docs/` | 原始文档资料、使用说明、长期维护的知识与结论 | 按主题组织,需要时区分 `references/` 与 `guides/` |
| `data/` | 项目中的各类数据与运行结果 | 遵循通用的渐进组织、渐进披露原则,具体结构在项目中确定 |
| `dist/` | 构建生成的可运行或可发布程序包/站点 | 内部结构由构建工具管理,通常在首次构建时生成 |

建议新空项目的 init 创建根入口、完整 spec 核心以及 `src/`、`tests/`、`docs/`、`data/`。它们明确了文件的大类归属,无需推测业务模块。`dist/` 作为约定保留,由构建产生,不预建内容或规则文件。下级目录随真实内容建立。

```text
project/
├── README.md
├── AGENTS.md
├── CLAUDE.md
├── handoff.md
├── spec/                  # 沿用现有 README / INDEX / 规则 / needs / ADR
├── src/
├── tests/
├── docs/
├── data/
└── dist/                  # 有构建时由工具生成,不是 init 预建目录
```

不再默认创建顶层 `scripts/`、`reference/`、`outputs/`、`build/`。这是新项目默认约定,不是删除或迁移已有目录的命令。本仓已有 reference 素材库不在本轮整理范围内。

对于已有 `app/`、语言包目录或就近测试布局的项目,沿用其合理组织方式,避免补出第二套职责相同的目录。已有项目的补建判定需在 CLI 实现时明确并覆盖测试;不要提前声称已有自动识别能力。框架输出路径可以正常配置时优先 `dist/`;框架有强制约定时服从工具,不手工搬动构建内容。

## 3. src 的组织原则:职责内聚、减少耦合

用普通语言表达:

- 完成同一件事、经常一起修改的代码放在一起。
- 不同模块尽量通过少量明确接口协作,减少对彼此内部细节的依赖。
- 多处确实需要且职责稳定的能力再共享;优先使用明确名称,如 `storage/`、`formatting/`,避免把不相关代码不断塞入 `utils/` 或 `common/`。

`spec/needs/` 管需求生命周期,`src/` 管长期能力。一项需求可以跨模块,一个模块可以服务多个需求,不强制一一对应。不要按需求编号、开发阶段建立 `src/need-001/`、`src/phase2/`。

例如 `src/orders/` 内可以同时有订单计算和订单导入入口。辅助脚本就近放到所属能力中并复用实现,不需要另建顶层 scripts。起初只有单一职责的少量代码可以用文件,出现独立职责、依赖或测试需要再升为目录;不要预建一套空分层。

`tests/` 可按能力或测试场景组织,既可以对一个模块进行单独验证,也可以跨多个模块验证完整流程。频繁测试并不要求测试文件与源码文件逐个对应。测试夹具放在测试所属范围;批量测试报告等运行产物归入 data 的对应任务或工具约定位置。

## 4. data 的统一约定

数据与运行结果统一放在 `data/`。AE 只定义这一级职责,内部按具体项目需要渐进组织、渐进披露,避免无关内容长期平铺,不规定子目录名称或固定层级。

`data/` 承载数据与运行结果,`dist/` 承载构建出的程序或发布包,`docs/` 承载文档资料与长期维护的知识。具体保存、清理与版本管理策略由项目根据实际内容确定。

## 5. 根 AGENTS.md 的通用规则

已在本仓根 AGENTS.md 加入以下一条规则,建议后续 init 模板采用同一语义:

> **目录按职责聚合、信息渐进披露**:除已有明确规范、框架约定或工具生成的目录外,手工维护的文件按职责或主题组织,避免无关文件长期平铺;入口保留概要与导航,细节随复杂度按需下沉,不为分层而分层;新增或修改时检查涉及范围的归属与边界,调整结构同步相关引用与说明。

两个概念各自解决不同问题:

- **渐进组织/拆分**:内容有独立职责或主题后再分组,少量相关文件可以同层,不为每个文件建立一层目录。
- **渐进披露**:入口提供足够判断下一步阅读位置的概要与导航,细节在相应模块中按需展开。单纯增加文件夹不会自动实现信息披露。

适用范围是手工维护的 src、tests、docs、data 等内容。spec 已有专门规范,遵守该规范;dist 等构建目录由工具决定内部结构,修改源码或构建配置后重新生成,不手动整理生成文件。根配置文件也遵循其工具约定。

因此规则不写成“所有文件禁止平铺”或“所有目录都加 README/AGENTS.md”。这类绝对要求会鼓励无意义的深层目录和重复文档,反而提高使用成本。

默认不新增 `src/AGENTS.md`、`docs/AGENTS.md`、`data/AGENTS.md`。只有子树存在专属且不能简洁放入根规则的约束时再下沉;通用规则保持单点维护。

根 AGENTS.md 发布模板从完全空白变成含一条结构原则,是本轮方向对现有设计的调整。没有恢复路由器指针或整套预设章节。

补充边界:子目录规则文件是否自动读取依赖平台;OpenAI 官方说明启动时按项目根到当前工作目录构建指令链,不应推广为所有后代目录自动加载。后续若引入局部规则,仍需验证实际查阅路径。[官方来源](https://learn.chatgpt.com/docs/agent-configuration/agents-md)(2026-09-09 核对;本轮未新增运行时验证)。

## 6. 持续治理与事实来源

根规则覆盖所有修改,包括快修、一次性脚本,不要求它们都进入 S1。设计与收口沿用已有步骤:

- 设计时明确新增文件的所属模块、公开接口与依赖变化,在现有 writing-plans 的 File Structure 中表达。
- 修改时检查涉及范围有无职责混杂、重复实现、越过接口依赖内部细节等问题。
- 收口时同步受影响的引用、入口、测试与目录说明;跨项目的大范围重构另记方案,不因一条通用规则自动重排全仓。

拆分依据是职责、变化原因、测试独立性与依赖关系。行数或文件数量可作提醒,不作为自动拆分阈值。共享抽象在实际复用关系稳定后提取,不为统一外观提前抽象。

继续沿用现有信息分工:

| 入口 | 内容 |
|------|------|
| 根 README.md | 项目定位、用法与简短目录导航 |
| 根 AGENTS.md | 通用操作约束与必要阅读入口 |
| spec/README.md | 全局能力/架构地图,需要时链接更细的说明 |
| 单需求 design.md | 局部模块、接口、数据流与技术取舍 |
| spec/ADR/ | 跨需求的长期架构决策 |
| docs/ | 文档类输入、使用说明与维护中的知识 |
| handoff.md | 最新当前态与下一步 |

避免额外维护一份相同的架构总览。目录说明优先放在最近的已有入口,只有信息确实复杂时才增加局部 README。
