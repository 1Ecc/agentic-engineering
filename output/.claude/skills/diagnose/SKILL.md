# Diagnose

针对疑难 bug 的方法论纪律。只有在有明确理由时才能跳过某个阶段。

探索代码库时，参考项目的领域术语表建立相关模块的清晰心智模型，并检查所触及范围内的 ADR。

## Phase 1 — 建立反馈回路

**这一步就是这个 skill 的精髓。** 其他都是机械操作。如果你有一个**快速、确定性、agent 可执行**的 bug pass/fail 信号，你就能找到根因——二分定位、假设检验、插桩都只是消费这个信号。如果没有，再怎么盯着代码也救不了你。

在这一步投入不成比例的精力。**要进取、要有创意、绝不放弃。**

### 构建反馈回路的方法 —— 大致按以下顺序尝试

1. **失败测试**：在能触达 bug 的任意接缝写——单元、集成、e2e 都可以。
2. **Curl / HTTP 脚本**：打到正在运行的 dev 服务器。
3. **CLI 调用**：用固定输入（fixture），把 stdout 跟已知好的快照做 diff。
4. **无头浏览器脚本**（Playwright / Puppeteer）——驱动 UI，断言 DOM / console / network。
5. **重放捕获的 trace**：把真实网络请求 / payload / 事件日志存盘，隔离地通过代码路径重放。
6. **一次性 harness**：跑起系统的最小子集（一个服务 + mock 依赖），用一次函数调用就能命中 bug 代码路径。
7. **Property / fuzz 循环**：如果 bug 是"有时输出不对"，跑 1000 个随机输入找失败模式。
8. **二分定位 harness**：如果 bug 出现在两个已知状态之间（commit / 数据集 / 版本），自动化"启动到状态 X、检查、重复"，这样可以 `git bisect run`。
9. **差分循环**：同一个输入跑老版本 vs 新版本（或两套配置），diff 输出。
10. **HITL bash 脚本**：最后手段。如果必须人手点击，用 `scripts/hitl-loop.template.sh` 驱动**用户**，让循环依然结构化。捕获的输出回喂给你。

把反馈回路建对了，bug 就解决了 90%。

### 迭代回路本身

把回路当产品。一旦你有了**一个**回路，问自己：

- 能不能更快？（缓存初始化、跳过无关 init、缩窄测试范围。）
- 信号能不能更尖锐？（断言具体 symptom，而不是"没崩"。）
- 能不能更确定性？（固定时间、固定随机种子、隔离文件系统、冻结网络。）

30 秒的不稳定回路只比没回路勉强好一点。2 秒的确定性回路是 debug 超能力。

### 非确定性 bug

目标不是干净复现，而是**更高的复现率**。把触发跑 100 次、并行、加压、缩窄时序窗口、注入 sleep。50% 抖动的 bug 可调；1% 不可调——一直把复现率拉高直到可调为止。

### 当你确实建不起回路

停下来，明确说出来。列出尝试过什么。请用户提供：(a) 能复现的环境访问权限，(b) 一份捕获产物（HAR 文件、日志 dump、core dump、带时间戳的录屏），或 (c) 允许临时加生产环境插桩。**没有回路，绝不**往下做假设。

没有可信的回路，不要进入 Phase 2。

## Phase 2 — 复现

跑回路。看着 bug 出现。

确认：

- [ ] 回路产出的失败模式是**用户**描述的那个——而不是附近碰巧出现的另一个失败。错的 bug = 错的修复。
- [ ] 失败在多次运行间可复现（非确定性 bug 则需要可复现到足以调试的频率）。
- [ ] 你已经捕获了精确的 symptom（错误信息、错误输出、慢的时序），以便后续阶段验证修复确实解决了它。

bug 没复现，不要往下走。

## Phase 3 — 假设

测试任何假设之前，**先列 3-5 个排序后的假设**。只生成一个假设会锚定在第一个看起来合理的想法上。

每个假设必须**可证伪**：说出它的预测。

> 格式："如果 <X> 是根因，那么 <改 Y> 会让 bug 消失 / <改 Z> 会让 bug 加剧。"

如果你说不出预测，这个假设就是 vibe——丢掉或锐化它。

**测试前把排序列表给用户看。** 用户经常有领域知识能瞬间重排（"我们刚部署了影响 #3 的改动"），或者知道哪些假设已经被排除过。便宜的 checkpoint，省大量时间。别卡在这等——用户离线就按你的排序往下走。

## Phase 4 — 插桩

每个探针必须对应 Phase 3 的某个具体预测。**一次只改一个变量。**

工具优先级：

1. **调试器 / REPL 检查**，如果环境支持。一个断点胜过十条日志。
2. **定向日志**，在能区分假设的边界打。
3. 绝不"全打日志再 grep"。

**每条 debug 日志加唯一前缀**，比如 `[DEBUG-a4f2]`。清理时一次 grep 搞定。不带前缀的日志会残留；带前缀的会被清。

**性能分支。** 性能回归场景下日志通常是错的工具。换做法：先建立基线测量（timing harness、`performance.now()`、profiler、查询计划），再二分定位。先量再修。

## Phase 5 — 修复 + 回归测试

**在修复之前**写回归测试——但只在有**正确接缝**的情况下。

正确接缝是指：测试在调用点用**真实 bug 模式**去触发。如果可用的接缝太浅（bug 需要多 caller 触发却用单 caller 测试、bug 需要触发链条却用单元测试模拟不出来），在那里写回归测试给的是虚假信心。

**如果没有正确接缝，这件事本身就是 finding。** 记下来。代码库架构正在阻止 bug 被锁定。把这条 flag 给下一阶段。

如果有正确接缝：

1. 把最小化复现转成在该接缝写的失败测试。
2. 看它失败。
3. 应用修复。
4. 看它通过。
5. 再跑一次 Phase 1 的反馈回路，针对原始（未最小化）场景。

## Phase 6 — 清理 + 复盘

宣告完成前必须做：

- [ ] 原始复现不再复现（重跑 Phase 1 回路）
- [ ] 回归测试通过（或文档化记录"无接缝可用"这件事）
- [ ] 所有 `[DEBUG-...]` 插桩已清除（grep 那个前缀）
- [ ] 一次性原型已删除（或移到明确标记的 debug 位置）
- [ ] 最终被证实正确的那个假设写到 commit / PR 信息里——让下一个 debugger 学到
- [ ] 把本次诊断结论落到 `openspec/changes/<name>/issues/<topic>.md`
      - 已有相关主题文件 → 追加更新（不开新文件）
      - 无 → 新建 `<topic>.md`，topic 名简短可识别
      - 内容按本次诊断自然写，无固定模板


**然后问：什么本可以预防这个 bug？** 答案分两种沉淀路径：

- 涉及架构变更（缺少好的测试接缝、调用方纠缠、隐藏耦合）→ 交给 `/improve-codebase-architecture` skill
- 跨周期、跨 change 还会被引用的关键决策 → 建 `openspec/adr/<NNNN>-<title>.md`

修复**落地之后**再给建议——你现在的信息比开始时多。
