# to-task

## 输入

调用方应提供：

- 方案文档的路径或内容（设计 / RFC / PRD / spec 都可以）。未特定指定时，默认读取 `proposal.md` / `design.md` / `specs/`
- 产物落盘位置；未特定指定时，落到 `openspec/changes/<change-name>/tasks.md`

## 输出格式

```
- [ ] <动词开头的描述>
  - 验收: <做完后如何验证，具体到可执行>
```

例：

```
- [ ] 1.1 添加 users 表的 schema migration
  - 验收: 跑 migration 后 `\d users` 显示 id/email/created_at 三列且 email 有 unique 索引
```

按方案文档的天然段落分组：`## <分组名>`，组内编号 1.1 / 1.2 / 2.1 …

可选字段（按需添加，不必填）：

- `Depends on: <编号或描述>` —— 仅当该 task 在另一个 task 完成前**无法执行**
- `Files: <路径>` —— 仅当方案文档已明确指定到文件级

## 工作流

1. **读完整份方案再开始拆**。不要边读边产出 task，否则前面的 task 看不到后面的内容
2. **先 draft，不直接写文件**。在会话内输出清单
3. **请用户审视**。明确让用户回应三件事：
   - 哪些 task 太大该拆、哪些太小该合并
   - 方案里有哪条要做的事没被任何 task 覆盖
   - 有没有硬依赖漏标
4. **ack 后写盘**。如果同名文件已存在，先 diff 再覆盖

## 不做的事

- task 描述里不嵌代码片段
- 不预设执行风格（不替执行者决定 TDD / 提交节奏 / 测试策略）
- 不写"先 X 再 Y 再 Z"型描述——这意味着应拆成多个 task
