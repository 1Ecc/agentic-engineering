# S1 · 软件全生命周期主循环:两场景模型

> 框架索引:[../framework.md](../framework.md) · 场景定义 / S1

## 设计立意

S1 主循环 = **两个场景**,按问题来源天然切分,不按"做什么/怎么做对"的相位切分:

| 场景 | 何时进入 | 主问题 |
|------|----------|--------|
| **A · 需求场景** | 有一个明确"想做的事"(初始需求 / 新需求 / 子需求,粒度自由) | 把想法变成 spec → 变成代码 |
| **B · 验收场景** | 需求场景产出后,**用户亲自验收** | 验收通过则关闭;不通过则进入 debug 子路径 |

两场景串行 + 回流闭环:`A → B → (验收 OK 关闭) | (验收失败 → debug → 沉淀回流 → A 下一轮)`。

---

## 场景 A · 需求场景

**触发**:一个明确的"想做的事"

**入产物**:一句话级的想法

**出产物**:可运行代码 + 测试全绿(非 mock、端到端) + prd / design / todo 已落盘 + `spec/INDEX.md` 已更新

**节点路径(SDD 收敛 → 任务拆解 → TDD 执行 → 端到端验证)**:

```
想法
  │
  ├─ A1. 需求对齐
  │       与用户对齐"做什么、给谁用、解决什么问题、不做什么"
  │       skill:粗对齐 → brainstorming;涉接口/字段/参数等细节 → grill-me
  │       ── 门禁:未对齐不进 A2
  │
  ├─ A2. prd.md 落盘
  │       把对齐结果固化为"需求层 spec"(产品/业务视角,WHAT)
  │       归档到 spec/needs/<需求名>/prd.md
  │       skill:to-prd
  │
  ├─ A3. 技术设计 + design.md 落盘(合并)
  │       方案选型 + 局部架构(HOW,含关键接口、数据流、依赖)
  │       直接落盘到 spec/needs/<需求名>/design.md
  │       skill:writing-plans(只产 design,不产 todo)
  │       ── 门禁:技术方案未对齐不进 A4(必要时与用户确认关键取舍)
  │
  ├─ A4. 任务拆解 → todo.md
  │       读 design.md 拆出可执行任务清单
  │       归档到 spec/needs/<需求名>/todo.md(滚动维护,无状态字段)
  │       skill:to-issues
  │
  ├──────── 以上为 SDD,以下为 TDD ────────
  │
  ├─ A5. 执行(TDD 内循环)
  │       按 todo.md 推进,每项任务内部走 red → green → refactor
  │       —— 内部节奏不再单列节点;从用户视角就是"开发"
  │       skill:tdd
  │
  └─ A6. verify
          端到端真实路径验证(禁止 mock 绕过根因)
          skill:verification-before-completion
```

**关键设计**:
- **两层 spec + 一份任务清单**:prd(WHAT) / design(HOW) / todo(任务化);三份文件同一需求目录下
- **A3 合并设计与落盘**:实操中"设计 + 落盘"一气呵成,不再拆 A3/A4 两节点
- **两道硬门禁**都在 SDD 内:A1 需求未对齐 ⇒ 不写 prd;A3 技术方案未对齐(若涉及关键取舍)⇒ 不写 design
- **A5 执行节奏不锁**:内部 red/green/refactor 可来回,但要按 todo 推进、每项完成打勾
- **A6 verify 必须非 mock**(端到端验证,不能省)
- spec 长度不强求——一句话也算合法,只要"做什么/怎么做"已显式写下并对齐

## 场景 B · 验收场景

**触发**:场景 A 产出后,用户**亲自**验收(开发者自验不算)

**入产物**:可运行代码 + 测试全绿 + spec 已落盘

**出产物(分支)**:
- 验收 OK ⇒ 当前需求关闭,`spec/INDEX.md` 已更新
- 验收失败 ⇒ 进入 **debug 子路径**,直到验收 OK + 沉淀完成

**节点路径**:

```
A 场景结束
  │
  ├─ B1. 用户验收
  │       用户按需求 spec 实际使用产物
  │
  ├─ 分支判断:
  │       ├─ ✅ 通过 ──► B-OK. 关闭 + INDEX 更新 ──► 进入下一轮(可能是新需求,回 A)
  │       │
  │       └─ ❌ 不通过 ──► 进入 B2(debug 子路径)
  │
  ├─ B2. 期望态对齐
  │       用户口头/文字反馈 → 与开发对齐"实际看到的 / 期望的是什么"
  │       skill:grill-me
  │       ── 门禁:期望态未对齐不进 B3(CES 硬规则)
  │
  ├─ B3. 根因定位
  │       根因优先:不绕过、不兜底、不硬编码;先复现 + 定位
  │       skill:diagnose(reproduce → minimise → hypothesise → instrument,
  │                    instrument 段覆盖断点/日志/二分等定位方法)
  │
  ├─ B4. issue 落盘(7 段格式)
  │       把 B2 + B3 的成果一次性写到 spec/needs/<需求名>/issues/<主题>.md
  │       此时 7 段已有:问题描述 / 当前态 / 期望态 / 分析与解决
  │       (to-issues / bug / 验收 在 B5-B6 滚动追加)
  │       skill:无(轻量整理动作;模板内容约定见 ../spec-framework.md)
  │
  ├─ B5. 修复
  │       按根因实施;过程中的小 bug 追加到 issue 文件的 bug 段,不开新专项
  │       skill:tdd(与 A5 复用)
  │
  ├─ B6. 用户复验
  │       用户实际验证;失败计数 +1
  │       └─ 仍失败 且 计数 < 2 ⇒ 回 B3(根因可能不准)
  │       └─ 仍失败 且 计数 ≥ 2 ⇒ grill-me 介入,回 B2 重新对齐期望态
  │       └─ 通过 ⇒ 进 B7
  │
  └─ B7. issue-close + 分流沉淀
        标"已验收" + 按内容类型分流:
          - 业务规则     → 反哺 prd.md(作为下一轮 A 的输入)
          - 技术决策     → 反哺 design.md;若影响多需求 → spec/ADR/
          - 复用性规则   → 候选 S2(用户确认后升 foundation)
        skill:review(双轴审查,后续个性化加分流落盘)
```

**关键设计**:
- 验收场景**默认就该跑**,不是可选——A 结束 ≠ 需求完成
- debug 是 B 的**子路径**,不是独立场景;入口由"验收失败"统一触发
- 7 段格式(问题描述 / 当前态 / 期望态 / 分析 / to-issues / bug / 验收)是硬约束;模板由 `diagnose` skill 的 `assets/issue-7-sections.md` 承载,B4 落盘时使用
- debug 中**偏离主题或子需求**不就地塞,作为新需求登记到 INDEX(下一轮 A 的输入)
- **B 子路径节奏 = 先做后落**:对齐(B2)+ 根因(B3) 都先在对话里推进,B4 才把成果按 7 段格式一次性落盘。与 A 场景"A1 对齐 → A2 prd 落盘"对称
- B6 复验失败 ⇒ 默认回 B3(根因可能不准);但**循环 ≥ 2 次**时,认为根因方向错误,grill-me 介入回 B2 重新对齐期望态——避免在错误方向上打转

## 两场景的关系

```
       ┌────────────────── 场景 A 需求 ──────────────────┐    ┌── 场景 B 验收 ──┐
       │                                                   │    │                │
想法 ─► A1 对齐 ─► A2 prd ─► A3 design ─► A4 todo ─► A5 执行 ─► A6 verify ─► B1 验收
                                                                                          │
                                                                                          ├─ ✅ ─► 关闭
                                                                                          │
                                                                                          └─ ❌ ─► B2-B6 debug
                                                                                                          │
                                                                                                          ▼
                                                                                                       B7 沉淀分流
                                                                                                          │
                          ┌── 业务规则反哺 prd ◄─────────────────────────────────────────────────────────┤
                          │── 技术决策反哺 design / ADR ◄────────────────────────────────────────────────┤
                          └── 复用规则 → 候选 S2 通用 skill ◄────────────────────────────────────────────┘
```

- **常态串行**:A → B,任一时刻 `spec/INDEX.md` 反映各需求所在节点
- **回流闭环**:B7 沉淀的规则成为下一轮 A 的输入信号(下一个需求/缺陷的起点)
- **不并行**:同一项目同一时刻只在一个场景里,避免多线程混乱
- **handoff.md ≠ INDEX**:INDEX 是项目结构态(各节点自动维护);handoff.md 是会话交接态(focus、待裁决问题、下一步建议),仅在会话结束时由 foundation 级 handoff skill 人工触发

## 验证(用方法论自身回答)

1. "用户说想加个新按钮" → 进哪个场景哪一步?
   → A1(需求对齐)
2. "上周上线的功能用户说排序不对" → 进哪个场景哪一步?
   → B2 期望态对齐(grill-me 跟用户对齐"实际看到什么 / 期望什么");不必重走 A
3. "技术方案我自己拿不准要选 Redis 还是本地缓存" → 在哪一步处理?
   → A3 技术设计阶段与用户对齐取舍,未定不进 A4
4. "debug 时发现原 prd 写漏了一个边界条件" → 怎么流?
   → B7 沉淀分流 → 业务规则反哺 prd.md(下一轮 A 的输入)
5. "debug 修完用户复验还是不对" → 回哪一步?
   → 第 1 次失败回 B3(根因可能没定准);第 2 次以上失败 grill-me 介入回 B2(期望态可能没对齐)
6. "design 里写了一个'本项目统一用 Postgres'的决策" → 应该放哪?
   → 上升到 spec/ADR/,因为它影响多个需求,不属于单个 design.md
7. "需求里出现了具体的接口和参数定义" → A1 用哪个 skill?
   → grill-me(细粒度对齐);整体意图阶段用 brainstorming
